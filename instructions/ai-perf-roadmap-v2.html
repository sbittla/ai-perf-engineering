When to use nsys
  • First step in any GPU bottleneck investigation — always start here
  • CPU↔GPU transfer bottlenecks: H2D/D2H taking disproportionate time
  • GPU idle gaps — DataLoader starving the GPU
  • Kernel launch overhead vs actual compute ratio

Linux Performance Tooling

The non-GPU toolkit that diagnoses everything starving your GPU — disk I/O, memory pressure, lock contention, CPU stalls.

Linux perf accesses hardware PMU counters directly from the CPU. No code changes required. Counts cache misses, branch mispredictions, instructions per cycle, and samples call stacks at configurable frequency.

GPU Architecture — Questions test whether you understand the hardware beneath PyTorch. A principal engineer doesn't just know the API; they understand why the hardware makes certain tradeoffs unavoidable and can trace a performance problem down to the silicon level.

The GPU memory hierarchy has four levels, each with drastically different bandwidth and latency. Understanding which level your kernel is accessing is the foundation of performance analysis.

Registers ~8 TB/s per SM, <1 cycle — fastest, private per thread, 256KB/SM on Ada (RTX 4060) L1/Shared ~19 TB/s per SM, ~5 cycles — 128KB/SM, programmer-controlled shared mem vs L1 split L2 Cache ~2.5 TB/s total, ~30 cycles — 32MB on Ada, unified across all SMs GDDR6/HBM ~272 GB/s total, ~200 cycles — RTX 4060 GDDR6; A100 = 2TB/s HBM3

The arithmetic intensity (FLOP/byte) determines which ceiling you hit. A matmul on large matrices has AI ~100+ — it's compute-bound; the roofline says peak FLOPs is the bottleneck. LLM decode on batch=1 has AI ~2 — it's memory-bound; you're moving weights from GDDR6 and the GPU spends most time waiting for data.

In practice: FlashAttention exploits this hierarchy explicitly. The softmax+attention output computation is tiled to fit in L1/shared memory, avoiding GDDR6 round-trips for intermediate attention scores. That's why it achieves ~3× speedup vs naive attention — not cleverness, but respecting the memory hierarchy.

This question tests how deep your mental model goes. Most engineers stop at "PyTorch calls CUDA" — a principal engineer traces every hop:

  • Python layer: model(x) calls the ATen dispatcher, which selects the appropriate kernel implementation (eager vs compiled) and data type.
  • CUDA Runtime: cudaLaunchKernel() is called with grid/block dimensions. This is a non-blocking CPU call — it enqueues the launch command into the CUDA stream's command buffer and returns immediately. The CPU doesn't wait.
  • GPU Command Processor: The GPU's hardware scheduler reads from the stream's command buffer. When resources are available (enough registers, enough shared memory), it assigns thread blocks to SMs.
  • SM Warp Scheduler: Each SM receives thread blocks. The SM's warp scheduler partitions threads into warps of 32. On each clock cycle, the warp scheduler issues instructions from one of 4 warp schedulers per SM (Ada architecture). If a warp stalls (waiting for L2 cache hit), another ready warp executes — this is latency hiding via occupancy.
  • Execution: FP16 matmuls are dispatched to Tensor Core units (4th gen on Ada). The Tensor Core performs a 4×8×16 matrix fragment multiply in a single cycle.

Key insight for debugging: The ~5–20µs gap between CPU submission and GPU start (visible in nsys as "kernel launch overhead") is the time for the command to travel from CPU → PCIe → GPU command processor → SM scheduler. For tiny kernels that take 10µs, this overhead dominates — which is exactly why torch.compile matters for elementwise ops.

Warp divergence occurs when threads within a 32-thread warp take different execution paths (if/else). Since all threads in a warp execute the same instruction at the same cycle (SIMT), the warp must serialize both paths with inactive threads masked off. In the worst case, throughput halves.

# Detect with ncu: ncu --metrics sm__sass_average_branch_targets_threads_uniform.pct python script.py # 100% = no divergence. Below 80% = investigate.

In LLM workloads specifically: The vanilla attention softmax has a conditional mask = (causal_mask == 0) applied to attention scores. In naive implementations, threads in the same warp may mask different positions, causing divergence in the masking logic. FlashAttention eliminates this by handling causal masking via tile-based indexing rather than per-element conditionals.

Dropout is another source: a random threshold per-element means threads diverge based on their random value. BF16 training with dropout p=0.1 at large batch sizes: the warp-level divergence is tolerable because the random pattern averages out. At small batch (batch=1 decode), you have very few warps, so divergence from any source hits harder.

  • Matters most: custom CUDA kernels with data-dependent branches, sparse attention patterns, variable-length sequence masking
  • Matters less: transformer matmuls (pure arithmetic, no branches), elementwise activations (GELU/ReLU use predicated instructions, not branches)
Follow-up: "How does torch.compile handle divergence in activation functions?" → Triton-generated kernels use predicated execution (tl.where) instead of branches, eliminating divergence while preserving correctness.

Occupancy = (active warps on SM) / (maximum warps an SM can hold). It's a proxy for latency hiding: high occupancy means when one warp stalls on a cache miss, another warp can execute instead, hiding the ~200-cycle DRAM latency.

Register usageIf each thread uses 64 registers, only 512 threads fit per SM (SM has 65,536 registers). At 256 threads/block → 2 blocks max.Reduce register usage; use -maxrregcount

When maximising occupancy doesn't help: If a kernel is compute-bound (SM throughput ≈ 100%), adding more warps just queues them up behind the already-saturated execution units. Optimising occupancy then hurts by reducing registers per thread (which may cause register spilling to slower memory). The classic example is a cuBLAS GEMM on large matrices — it's already at peak compute with moderate occupancy (50-70%).

The roofline model plots achievable FLOP/s against arithmetic intensity (FLOP/byte). It has two lines: the memory bandwidth ceiling (diagonal: throughput = BW × AI) and the compute ceiling (horizontal: throughput = peak FLOPs). Where they intersect is the ridge point.

Ridge point = Peak FLOPS / Peak BW RTX 4060: 136 TFLOP/s FP16 / 272 GB/s = 500 FLOP/byte If AI < 500 → memory-bound → reducing data movement helps If AI > 500 → compute-bound → only faster GPU or better kernel helps LLM decode (batch=1): AI ≈ 2-5 FLOP/byte → deeply memory-bound LLM prefill (batch=32, seq=2048): AI ≈ 200+ → compute-bound

How I use it in practice: First I get the roofline anchors empirically — measure peak BW with a cudaMemcpy benchmark and peak FLOPs with a large GEMM. Then for any slow kernel, I compute its AI from FLOPs (2×M×K×N for matmul) and bytes accessed. If it's left of the ridge, I ask: what's re-loading data it already has? Can I increase tile size to improve reuse? If it's right of the ridge, I ask: is there a more efficient algorithm (e.g., Flash Attention's O(1) memory algorithm)?

Common mistake: Computing AI based only on unique data (ignoring repeated reads). If your kernel reads the same tensor 3 times because you don't tile, the real AI is 3× worse than the theoretical AI.

Tensor Cores are dedicated matrix multiply-accumulate units that perform a 4×8×16 (or 16×8×16) matrix fragment multiply-add in a single cycle. Regular CUDA cores do one multiply-add per cycle per lane. The theoretical throughput difference is 8–16× for FP16/BF16 workloads.

Why transformers benefit disproportionately: The dominant operations in a transformer layer are matrix multiplications — QKV projections, attention scores, output projections, and the FFN. These are exactly what Tensor Cores are designed for. A 7B parameter model spends ~90% of its FLOP budget in GEMMs.

Requirements to use Tensor Cores: 1. Input dtype must be FP16, BF16, TF32, or INT8 (NOT FP32) 2. Matrix dimensions must be multiples of 8 (16 for best utilisation) 3. cuBLAS handles this automatically when you call torch.mm(a.half(), b.half()) Verify Tensor Cores are active: ncu --metrics sm__pipe_tensor_cycles_active.avg.pct_of_peak_sustained_active script.py Should be >50% for transformer workloads at FP16

Practical trap: A common bug is having even one FP32 operation in the critical path that forces the matmul to fall back to CUDA cores. Debug by checking the profiler for kernel names — ampere_sgemm_* = Tensor Core GEMM; volta_sgemm_* = CUDA core fallback (mismatched dtype).

Follow-up: "What's TF32 and how does it differ from FP16?" → TF32 uses FP16 range but FP32 mantissa bits; automatically used by cuBLAS for FP32 inputs on Ampere+. Gives ~10× speedup over full FP32 with no code changes, but still 3× slower than FP16 because inputs are still 4 bytes wide.

When 32 warp threads each load one float, the hardware checks if their addresses are contiguous. If so, it coalesces all 32 loads into a single 128-byte transaction (one cache line). If addresses are scattered, it issues up to 32 separate transactions — 32× more memory bus traffic for the same data.

Stride-1 access (coalesced): Thread 0 → addr[0], Thread 1 → addr[1], ..., Thread 31 → addr[31] → ONE 128-byte transaction — uses full bus width Stride-32 access (uncoalesced): Thread 0 → addr[0], Thread 1 → addr[32], ..., Thread 31 → addr[992] → THIRTY-TWO 128-byte transactions — 32× more BW used for same data Measure with ncu: ncu --metrics l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum python script.py # Sectors requested vs ideal tells you coalescing efficiency

Where this bites LLM code: Transposed weight matrices. If a Linear layer stores weights as (d_out, d_in) but you access them (d_in, d_out) during inference, you're doing column-major access = stride = d_in between consecutive thread accesses = terrible coalescing. cuBLAS handles this with the transposable GEMM API, but custom kernels need to be aware.

Another trap: The KV cache in paged attention. Pages are scattered in memory by design. When the attention kernel reads K, V from non-contiguous pages, coalescing degrades. This is why PagedAttention requires careful memory layout planning and why there are ongoing efforts to improve page-aligned access patterns.

Follow-up: "How does the tensor memory layout (contiguous vs non-contiguous) affect coalescing?" → A tensor after .transpose() is non-contiguous — its strides don't match its logical layout. Operations on it generate uncoalesced accesses. .contiguous() forces a copy into a coalesced layout; it's worth the copy cost when the tensor will be read many times.

Kernel fusion combines multiple operations into a single GPU kernel, eliminating the intermediate writes to and reads from HBM between operations.

Unfused (3 separate kernels): x = relu(x) → write x to GDDR6 (256MB) x = x / x.std() → read from GDDR6, compute, write (256MB × 2) x = dropout(x) → read from GDDR6, compute, write (256MB × 2) Total: 5 × 256MB = 1.28 GB moved Fused (1 kernel): x = fused_relu_norm_dropout(x) Total: 2 × 256MB = 0.51 GB moved ← 2.5× less memory bandwidth

What torch.compile fuses: Pointwise operations (add, mul, relu, gelu, etc.) across any chain of elementwise ops. It uses TorchInductor's Triton backend to generate a single kernel for the entire chain.

What it can't fuse (graph breaks):

  • Data-dependent control flow: if tensor.sum() > 0: — requires materializing the tensor value before branching.
  • Custom Python functions without graph capture: Any Python code that isn't a recognized PyTorch op causes a graph break.
  • In-place operations on inputs: x.copy_(y) on a tensor used earlier in the graph causes aliasing issues.
  • Dynamic shapes by default: First pass compiles for shape (8, 64); second pass with (8, 128) may recompile if dynamic=False.

How to diagnose graph breaks: TORCH_LOGS=graph_breaks python script.py — prints every point where the graph was broken and why. Fixing graph breaks is often the highest-leverage optimization for torch.compile performance.

Follow-up: "Flash Attention is often cited as a fusion optimization. What specifically does it fuse?" → QK score computation, causal masking, softmax, attention-value multiply — all fused into tiles that fit in SRAM, so intermediate attention scores (B × H × T × T) never go to GDDR6. For T=2048, this avoids 2048² × B × H × 2 bytes of GDDR6 traffic per layer.

My diagnosis process is layered — coarse to fine, system-wide to kernel-level. Skipping layers wastes time.

  • Step 1 — Is the GPU being used at all? watch -n 0.5 nvidia-smi. If GPU util is below 50%, I'm not looking at a GPU problem — it's DataLoader, CPU preprocessing, or Python overhead. Fix those first.
  • Step 2 — System-wide timeline (nsys). nsys profile --stats=true python script.py. The stats table shows time distribution across kernel types and H2D transfers. The timeline shows whether GPU is idle between kernels (CPU-bound gap) or has continuous CUDA activity.
  • Step 3 — CPU flamegraph if gaps detected. py-spy record -o flame.svg -- python script.py. Wide bars at the top reveal which Python function is causing the gap.
  • Step 4 — Identify the slow kernel from nsys.** Once I know which kernel name dominates (e.g., ampere_sgemm_128x64), I profile only that kernel with ncu.
  • Step 5 — Kernel deep-dive (ncu). ncu --set roofline --kernel-name ".*slow_kernel.*" script.py. This tells me: is it memory-bound (dram throughput high), compute-bound (SM throughput high), or occupancy-limited?
  • Step 6 — Fix based on root cause. Memory-bound → reduce data movement (fusion, tiling, quantization). Compute-bound → Tensor Cores, FP16, better algorithm. Occupancy-limited → reduce register/shared memory per block.

The most common mistake I see: people jump straight to ncu on every kernel without first checking if the GPU is even busy. I've seen teams spend weeks optimizing kernel efficiency when the real problem was a DataLoader that fed the GPU at 20% utilization — fixing the DataLoader gave a 5× speedup before touching a single kernel.

Follow-up: "What if nsys shows the GPU is 95% utilized but performance is still below expectations?" → The problem is efficiency within the GPU activity. Check ncu for SM throughput — if it's 30%, you have an occupancy or memory access problem even while the GPU is "running". The GPU can be busy doing things inefficiently.

GPU operations are asynchronous by default. The CPU submits work to the GPU command queue and returns immediately — the GPU hasn't started executing yet. This is the source of every GPU timing mistake.

WRONG — most common mistake: t0 = time.time() result = model(x) ← CPU submits to queue, returns in ~5µs elapsed = time.time() - t0 ← measures CPU submission time, NOT GPU work STILL WRONG — slightly less wrong: t0 = time.time() result = model(x) torch.cuda.synchronize() ← forces CPU to wait for GPU to finish elapsed = time.time() - t0 ← better, but includes Python overhead (~0.5ms) CORRECT — CUDA events on the GPU timeline: start = torch.cuda.Event(enable_timing=True) end = torch.cuda.Event(enable_timing=True) start.record() ← GPU timestamp inserted into stream result = model(x) end.record() ← GPU timestamp inserted into stream torch.cuda.synchronize() ← wait for GPU to process both events ms = start.elapsed_time(end) ← pure GPU execution time, no Python overhead

Additional subtleties:

  • Warmup: First 3-5 runs trigger CUDA JIT compilation, cuBLAS autotuning (finds fastest algorithm for this matrix size on this GPU), and OS cache population. Always discard.
  • Multiple streams: CUDA events time the specific stream they're in. If your model uses multiple streams, synchronize() waits for all streams.
  • Profiler overhead: Active profilers (nsys, ncu) add overhead. Benchmark with profiler disabled for production-representative numbers.
  • Thermal throttling: After 5-10 minutes of heavy load, GPU may throttle clocks. Measure sustained throughput, not burst.
Follow-up: "How do you ensure your benchmark is measuring steady-state performance, not burst?" → Run for 30 seconds, discard first 5 seconds, measure the remaining 25 seconds. Compare throughput at t=5s vs t=30s — significant drop means thermal throttling. Check nvidia-smi --query-gpu=clocks.sm --format=csv -l 1.

This is the classic "busy but inefficient GPU" scenario. nvidia-smi GPU utilization measures the percentage of time at least one warp is executing on the SM — it says nothing about how efficiently the available compute is being used.

Most likely causes, in order of probability:

  • Memory-bandwidth bottleneck: The kernel is waiting for GDDR6 data. SM is technically "active" but stalling on memory loads. ncu will show dram__throughput ≈ 100% and sm__throughput ≈ 30-40%.
  • L2 cache thrashing: Working set exceeds L2 (32MB on RTX 4060). Every memory access goes to GDDR6, maximizing DRAM throughput but preventing compute from keeping up with the data delivery rate.
  • Kernel launch overhead dominates: Many tiny kernels (< 10µs each). GPU is 95% active but each kernel does trivial work. The overall throughput is limited by the rate of kernel launches (~50K/second). nsys shows hundreds of tiny kernel blocks separated by tiny gaps.
  • Low SM efficiency despite high SM activity: Warp stalls from register spilling, L1 cache misses, or instruction dependencies. The SM is occupied but not doing useful work every cycle.
Diagnostic command: ncu --set full --kernel-name ".*slowkernel.*" python script.py Look for: sm__issue_active.avg.pct_of_peak_sustained_active ← actual instruction issue rate stall_memory_dependency.pct ← % cycles stalled on memory stall_no_instruction.pct ← % cycles SM has nothing to issue

I encountered this exact pattern on a production LLM serving system. nvidia-smi showed 97% GPU util but throughput was half expected. ncu showed stall_memory_dependency = 74% — the decode kernel was spending 74% of cycles stalled waiting for KV cache reads from GDDR6. Root cause: KV cache pages were fragmented in memory, causing uncoalesced access. Reordering KV pages to be contiguous per batch reduced the stall to 42% and improved throughput 1.6×.

Follow-up: "If it's memory-bandwidth limited and you can't change the algorithm, what's left?" → Quantize weights/activations to INT8 (2× less data per byte), use mixed-precision to keep some tensors in INT4 (4× less). The roofline ceiling for the bottleneck ops shifts right; the kernel may become compute-bound at INT4.

A flamegraph visualises statistical CPU profiling samples as a stacked call graph. The horizontal axis is time (not call order — functions are sorted alphabetically within a level for visual clarity). The vertical axis is call depth. Width = CPU time spent in that function plus all its children.

Reading rules: 1. Find the WIDEST bars at the TOP of each stack — those are hot leaf functions 2. Wide bar with NARROW children = the function itself is the bottleneck 3. Wide bar whose ENTIRE width is one child = just overhead from the parent; look at the child 4. Flat tops (many same-width columns) = parallel functions spending equal time 5. Blue in diff flamegraph = function ran LESS in the "after" profile (improvement) 6. Red in diff flamegraph = function ran MORE (regression or new code path)

Interpreting a PyTorch training flamegraph in practice:

  • DataLoader.__iter__ wide → DataLoader is the bottleneck, not the model
  • transforms.ColorJitter wide under DataLoader → CPU augmentation is the slow part of DataLoader; move to GPU (torchvision v2)
  • cudaStreamSynchronize wide → excessive synchronization; find and remove .item() calls in the training loop
  • cudaMalloc scattered → memory fragmentation; use pre-allocated buffers
  • GIL wait wide → multiple threads competing for Python GIL; reduce num_workers or use spawn multiprocessing

Common mistake: Focusing on the widest bar without checking context. I've seen engineers optimise a 5% wide json.loads when the 60% wide DataLoader tower right next to it was the real problem. Always start with the widest tower, not the most interesting function name.

Follow-up: "What's the difference between a CPU flamegraph and what you see in the nsys timeline?" → nsys timeline shows GPU-level events (CUDA kernel launches, H2D/D2H transfers) on a wall-clock timeline. Distributed profiling requires collecting profiles from all ranks and correlating them by time. The challenge is that a bottleneck on rank 3 forces all other ranks to wait, and without synchronized profiling you'll see "idle" on rank 0 without knowing why.

  • Nsys with --trace=nccl on all ranks. NCCL_DEBUG=INFO nsys profile --trace=cuda,nvtx,nccl torchrun script.py — generates a report per rank. The NCCL trace shows all-reduce and all-gather calls. LLM Inference Systems — The questions most specific to this role. A principal engineer has designed or operated LLM serving systems at scale and can reason about the full stack: hardware, KV cache, batching strategy, quantization, and deployment tradeoffs.

This is the most important concept for LLM inference performance. Prefill and decode are two phases of the same generation call, but they have completely opposite hardware bottlenecks.

PREFILL (process input prompt): Input shape per layer: (batch, T_prompt, d_model) — T_prompt tokens processed in PARALLEL Arithmetic intensity: 2 × batch × T × d / (weights + activations) → HIGH AI → COMPUTE-BOUND Bottleneck: tensor core throughput (FLOPs) Optimization: FP16, tensor cores, torch.compile, larger batch DECODE (generate tokens one at a time): Input shape per layer: (batch, 1, d_model) — ONE token per step Arithmetic intensity: ~2 FLOP/byte → deeply MEMORY-BANDWIDTH BOUND Bottleneck: GDDR6/HBM read bandwidth (loading model weights + KV cache each step) Optimization: quantization (reduce bytes/weight), batching, speculative decoding

Why this matters in practice: Optimizing for prefill (e.g., maximizing matmul throughput) does nothing for decode latency, which is what users perceive as "time between words." Conversely, INT4 quantization dramatically improves decode throughput (weights are 4× smaller → 4× less GDDR6 traffic per token) but has minimal impact on prefill throughput for large batches.

The practical implication for serving: A KV cache optimized serving system (like vLLM) separates these phases — prefill is scheduled in large chunks to keep GPU compute busy; decode is batched across many in-flight requests to keep GPU memory bus busy. The scheduler's job is to balance these two phases so neither starves.

Follow-up: "If a user is complaining about high TTFT (time to first token), which phase do you optimize?" → TTFT = prefill latency. It's compute-bound, so: use larger GPU, enable FP16/BF16, ensure Tensor Cores are active, consider chunked prefill to pipeline with ongoing decode requests. TTFT is different from TBT (time between tokens) which is the decode phase and is memory-bandwidth bound.

The KV cache stores computed Keys and Values from past tokens so they don't need recomputation on each decode step. Without it, generating token N would require a full forward pass over all N-1 previous tokens — O(N²) total work for a sequence of length N.

KV cache size per token: bytes = n_layers × 2 × n_heads × head_dim × dtype_bytes Llama-2-7B (FP16): 32 × 2 × 32 × 128 × 2 = 524,288 bytes = 512 KB per token Total for a request at sequence length T: request_kv = T × 512KB (for Llama-2-7B) At T=2048: 1GB per request — this is why serving 8GB GPUs is tight Total across concurrent requests: kv_pool = (GPU_VRAM - model_weights) × gpu_memory_utilization RTX 4060, INT4 Llama-7B: (8GB - 3.5GB) × 0.85 ≈ 3.8GB KV pool Max concurrent: 3.8GB / 1GB = ~3-4 requests at T=2048

Tuning in vLLM:

  • --gpu-memory-utilization 0.85 — what fraction of VRAM to reserve for KV cache. Increasing to 0.90 gives ~18% more KV pool. Don't go above 0.92 or OOM risk increases with fragmentation.
  • --max-model-len 2048 — limits the max context per request. Reduces the maximum a single request can consume, allowing more concurrent requests at shorter contexts.
  • --enable-prefix-caching — reuses KV blocks for identical prefixes (system prompts). For a system prompt of 500 tokens shared across all requests, this saves 500 × 512KB = 250MB per request.
  • --quantization awq — AWQ INT4 weights reduce from 14GB to 3.5GB, freeing 10.5GB for KV cache, enabling ~10× more concurrent requests.
Follow-up: "Why does PagedAttention improve the effective KV cache capacity compared to static allocation?" → Static allocation pre-reserves max_seq_len blocks for every active request. If max_seq_len=2048 but average response is 200 tokens, 90% of reserved KV memory is wasted. PagedAttention allocates 16-token pages on demand; a 200-token response uses only 200/16 = 13 pages instead of 128. This typically enables 3-5× more concurrent requests from the same VRAM budget.

Static batching (HuggingFace generate()) groups requests into a batch that must run until ALL requests complete. This forces padding: if one request needs 500 tokens and another needs 10, the 10-token request's GPU compute continues for 490 useless padding steps.

Static batch waste calculation: Batch of 16, max_output=500, avg_output=80 Useful token-steps: 16 × 80 = 1,280 Total token-steps: 16 × 500 = 8,000 Efficiency: 1,280 / 8,000 = 16% ← 84% waste Continuous batching: Request finishes → immediately evicted, new request joins next step Batch always has ~16 REAL requests generating REAL tokens Efficiency: ~90-95% ← near zero waste

Implementation detail: Continuous batching requires that the model can operate with a heterogeneous batch — different requests at different positions in their decode step, with KV caches of different lengths. This is exactly what PagedAttention enables: each request's KV cache grows independently, and the scheduler inserts and evicts requests mid-batch.

The scheduling challenge: When a short request finishes and a new one joins, the new request needs prefill (compute-intensive) while others are decoding (memory-bandwidth intensive). Naively interleaving these at every step hurts both phases. vLLM's scheduler uses chunked prefill: it breaks long prefills into chunks and interleaves with decode steps to prevent TTFT from spiking for decode requests while a new long prompt is being processed.

Follow-up: "What's the throughput improvement you typically see when moving from static to continuous batching?" → Typically 3-5× on production traffic with real (variable-length) outputs. The improvement is highest when output length variance is high — chatbot workloads with mix of 10-word and 500-word responses. For uniform-length outputs (e.g., always generate exactly 100 tokens), the improvement is minimal.

Speculative decoding addresses the fundamental inefficiency of decode: each step produces exactly one token, leaving the GPU largely idle. The insight is that a small draft model can generate K tokens cheaply; the large target model then verifies all K in one parallel forward pass.

Algorithm (4 steps per speculative step): 1. Draft model generates K tokens autoregressively (fast, small model) 2. Target model runs ONE forward pass on [prompt + K draft tokens] 3. Rejection sampling: accept draft token i if rand() < P_target(tok_i) / P_draft(tok_i) 4. If all K accepted: emit K+1 tokens (K draft + 1 bonus from target) If token j rejected: emit j tokens + resample from (P_target - P_draft) Expected tokens per verify step: E[tokens] = (1 - α^(K+1)) / (1 - α) α=0.8, K=5: E[tokens] = 3.6 → 3.6× decode throughput α=0.5, K=5: E[tokens] = 1.97 → 2× decode throughput α=0.2, K=5: E[tokens] = 1.25 → marginal gain

When it works well:

  • Target model is large and memory-bandwidth limited on decode (the verify step is cheap relative to K standard decode steps)
  • Draft and target share the same tokenizer and distribution (e.g., Llama-7B draft, Llama-70B target)
  • Output is "predictable" — code completion, repetitive text, factual recall → α ≈ 0.8+

When it doesn't work:

  • High-temperature sampling (creative writing) → α ≈ 0.3-0.5 → marginal gain
  • Target model is compute-bound (the verify step costs as much as K decode steps)
  • Draft and target have mismatched distributions → poor acceptance rate
  • Very short outputs (< K tokens total) — setup overhead dominates
Follow-up: "How does vLLM implement speculative decoding?" → --speculative-model <draft_model_path> --num-speculative-tokens 5. The draft model runs in a separate compute stream, interleaved with the target model's decode batches. The reject-and-resample guarantee ensures output distribution is mathematically identical to target-only sampling — no quality tradeoff.

My decision framework:

  • Model fits in VRAM at FP16 with acceptable KV cache headroom → use FP16. No reason to quantize if you're not VRAM-constrained. Quantization always has some accuracy cost, however small.
  • Model fits in VRAM at FP16 but decode throughput is too low → INT8. For decode, throughput ≈ GPU_BW / bytes_per_weight. INT8 doubles decode throughput at <1% quality cost. Worth it almost always.
  • Model doesn't fit at FP16 but must run on this GPU → INT4 (AWQ preferred). 7B at INT4 = 3.5GB; fits comfortably on 8GB with room for KV cache. Use AWQ over GPTQ for better accuracy retention.
  • Production serving with strict SLA and calibration data available → static INT8. The calibration step takes 30 minutes but gives better activation quantization than dynamic, translating to better throughput without accuracy regression.

The INT4 trap: INT4 models often show higher peak token throughput than INT8, but can have higher latency variance. The dequantization overhead (INT4 → FP16 before matmul) adds ~10-15% latency per layer. For latency-critical real-time use, INT8 often has better P99 latency than INT4 despite lower peak throughput.

Follow-up: "How does AWQ outperform GPTQ at the same bit width?" → AWQ identifies the 0.1% of weights that have the highest impact on output (by measuring activation magnitude) and allocates more precision to them. GPTQ minimizes the weight-rounding error globally without considering which weights actually affect outputs. On reasoning-heavy benchmarks, AWQ retains ~0.3 fewer perplexity points than GPTQ at INT4.

The key tradeoff: Tensor parallelism adds latency to every layer (the all-reduce). For a 32-layer model with TP=4, each forward pass has 32 × all-reduce latencies. If your interconnect is fast enough (NVLink ≥ 600 GB/s), this is ~0.1ms total. Over PCIe (~32 GB/s), the same 32 all-reduces might take 10-20ms — longer than the compute. This is why tensor parallelism is only profitable within a node (NVLink connected GPUs) and pipeline parallelism is used across nodes.

Follow-up: "How does Megatron-LM implement tensor parallelism for the attention mechanism?" → Each GPU gets a subset of attention heads. GPU 0 handles heads 0-7, GPU 1 handles 8-15, etc. Each GPU computes its heads independently (no communication during attention). The all-reduce happens only at the output projection, aggregating partial results. This is called "sequence parallelism" when extended to the layer norm.

FSDP shards all three memory components across GPUs: parameters, gradients, AND optimizer states. DDP only shards gradients (all-reduce) but keeps full parameter and optimizer copies on every GPU.

Memory comparison for a 7B model, 8 GPUs: DDP: 7B × (4 + 4 + 8) bytes / GPU = 7B × 16 bytes = 112 GB per GPU (FP32 optim states) FSDP: 7B × 16 bytes / 8 GPUs = 14 GB per GPU FSDP all-gather happens: - Before each transformer layer's forward pass (collect full params from all GPUs) - After each layer's backward pass (reduce-scatter gradients back) - Between forward and backward: free the gathered params to save memory

When FSDP saves memory vs hurts performance:

  • Memory savings are always real: 8× reduction in parameter + gradient + optimizer memory for 8 GPUs. This enables training models 8× larger on the same hardware.
  • Performance penalty: The all-gather before each layer adds communication overhead. For compute-heavy workloads (large batch, large hidden dim), the computation time dominates and the all-gather overhead is negligible (< 5% slowdown). For memory-bandwidth-bound workloads (small batch, activation-checkpointing heavy), the all-gather can add 15-20% overhead.
  • Use DDP when: Model fits in GPU memory at FP16, batch size is large, and training time is critical. The simpler communication pattern of DDP (one all-reduce per backward) is more predictable and slightly faster.
  • Use FSDP when: Model exceeds single-GPU memory, you're using activation checkpointing already (you're already memory-constrained), or you're training with large optimizer states (e.g., Adam with per-parameter momentum).
Follow-up: "How does FSDP handle a layer that's too large to fit in one GPU's memory even transiently during the all-gather?" → FSDP's cpu_offload=CPUOffload(offload_params=True) keeps shards on CPU RAM and only moves them to GPU for computation. The tradeoff is PCIe transfer latency (~5-10× slower than keeping on GPU), but it enables training models that couldn't fit otherwise. For very large models, you combine this with gradient checkpointing.

  • Check NVLink topology. nvidia-smi topo -m. If any pair of GPUs shows "PHB" or "PIX" instead of "NV*" (NVLink), they're communicating over PCIe — the all-reduce ring must go through the slower path. Reorganize the ring to put NVLink-connected GPUs adjacent in the ring.
  • NCCL ring algorithm vs tree algorithm. For small tensors, NCCL uses a ring algorithm which saturates bandwidth well. For very large tensors (> 256MB), it may use a tree algorithm which has better latency but lower bandwidth. Override: NCCL_ALGO=Ring.
  • Gradient bucket size. DDP accumulates gradients and all-reduces when a bucket fills. Default bucket size is 25MB. If individual tensor gradients are 500KB each and you're triggering all-reduces for each small tensor separately, the latency overhead dominates. Increase: bucket_cap_mb=100 in DistributedDataParallel.
  • PCIe bandwidth contention. If GPUs share a PCIe switch, other PCIe transfers (H2D data, NVMe) compete. Run nccl-tests with and without DataLoader active to isolate.

Follow-up: "How do you overlap NCCL communication with backward computation in DDP to hide the latency?" → DDP registers gradient hooks that trigger all-reduce for each bucket as soon as the bucket's gradients are computed during backward — while later layers are still computing. A straggler rank in distributed training forces all ranks to wait at the synchronization point (all-reduce barrier), making the entire job as slow as the slowest GPU. This is one of the most impactful — and tricky — problems in distributed training.

  • Identify the straggler first. Log per-rank step times. The simplest approach: dist.all_reduce(torch.tensor([step_time]), op=dist.ReduceOp.MAX) — all ranks know the max step time. Compare with per-rank times to identify which rank(s) are slow.
  • Reproduce the slow rank in isolation. Disable distributed (run rank N's data shard on one GPU). If it's still slow, the bottleneck is local to that rank's workload (imbalanced data shard, hardware issue).
  • Check for hardware differences. GPU thermal throttling: nvidia-smi --query-gpu=clocks.sm,temperature.gpu --format=csv -l 1. A GPU with dust-blocked cooling may run 20% slower under sustained load. NVLink or PCIe errors: nvidia-smi --query-gpu=ecc.errors.corrected.total --format=csv.
  • Check for data shard imbalance. If batches from rank N have systematically longer sequences (e.g., in an NLP dataset with variable-length examples), that rank processes more tokens per step. Fix: use a data sampler that balances total token count across ranks, not just sample count.
  • Memory pressure. If rank N is memory-constrained (e.g., different model shard in pipeline parallelism, or more gradient accumulation steps), it may be hitting OOM fallback paths or more frequent CUDA allocations.
Follow-up: "How do you handle the case where the straggler is due to data preprocessing variability rather than computation?" → Use a curriculum sampler that puts long sequences early in training and short sequences later; balance step time not sample count. Alternatively, add padding to the max length within a batch but cap max batch tokens rather than max batch size — this caps per-step computation regardless of sequence length variation.
Linux & Systems — Tests whether you can operate at the OS level, not just the Python level. A principal engineer in an AI infrastructure role must be comfortable with kernel-level tools and understand how the OS affects GPU workloads.

NUMA (Non-Uniform Memory Access) means that on multi-socket servers, each CPU has memory directly attached to it, with lower latency for local accesses and higher latency (1.5-2.5×) for cross-socket (remote) access via the QPI/UPI interconnect.

Worst-case data path in a 2-socket GPU server: DataLoader workers (bound to socket 1 CPUs) → load image from DRAM on socket 1 → traverse QPI interconnect to socket 0 (~100GB/s, adds ~100ns latency) → traverse PCIe bus (attached to socket 0) to GPU 0 Best-case data path: DataLoader workers (bound to socket 0 CPUs via numactl) → load image from DRAM on socket 0 → traverse PCIe bus (directly, no QPI hop) → GPU 0 Speedup from binding: typically 1.5-2× H2D bandwidth

In practice on a DGX A100 (8 GPUs, 2 sockets): GPUs 0-3 are on socket 0, GPUs 4-7 on socket 1. Tensor parallelism groups should always stay within a socket to keep NVLink traffic local. Cross-socket tensor parallelism goes over slower PCIe, reducing the benefit.

How to diagnose NUMA issues: numastat -p $(pgrep python) — look at numa_miss vs numa_hit. High miss rate = processes accessing remote NUMA memory. Fix: numactl --cpunodebind=$(cat /sys/bus/pci/devices/0000:01:00.0/numa_node) --membind=same python train.py.

Follow-up: "How do you set NUMA binding for a torchrun multi-GPU job?" → CUDA_VISIBLE_DEVICES=0,1,2,3 numactl --cpunodebind=0 --membind=0 torchrun --nproc_per_node=4 train.py for the GPU-0-socket-connected GPUs. For cross-socket GPU groups, use separate numactl invocations per group in the torchrun launcher config.

When the system runs out of physical memory and swap, the Linux OOM (Out-of-Memory) killer selects a process to kill based on an "OOM score" — essentially which process is using the most memory and can be killed with least damage. Training jobs, which consume gigabytes of RAM for DataLoader prefetch buffers and model state, are prime OOM targets.

  • Prevent by sizing correctly: free -h before training. Ensure (DataLoader prefetch buffers) + (Python process heap) + (OS file cache) ≤ system RAM. Rule of thumb: leave 10-20% RAM headroom.
  • Adjust OOM score to protect training: echo -1000 > /proc/$(pgrep python)/oom_score_adj — sets OOM score to minimum, making the kernel highly reluctant to kill this process. Range: -1000 (never kill) to +1000 (kill first). Requires root.
  • Monitor memory pressure: vmstat 1 | awk '{print $7, $8}' — columns 7 and 8 are swap-in and swap-out. Any non-zero values mean RAM is exhausted and swapping. Training under swap pressure is 10-100× slower.
  • Reduce DataLoader memory footprint: Each worker preallocates a buffer equal to prefetch_factor × batch_size × image_size. At 8 workers, prefetch_factor=4, batch=64, 3×224×224 float32: 8 × 4 × 64 × 3 × 224² × 4 bytes ≈ 9.7GB. Reduce workers or prefetch_factor if hitting system RAM limits.
Monitor OOM risk: $ dmesg -T | grep -i "oom\|killed" # check if OOM killer fired $ cat /proc/$(pgrep python)/oom_score # current score $ vmstat 1 | awk '{print $7" "$8}' | grep -v "0 0" # swapping happening?
Follow-up: "How is GPU OOM different from CPU OOM and how do you handle it?" → GPU OOM (CUDA out of memory) is handled by PyTorch at the CUDA allocator level. The allocator tries cudaMalloc, fails, calls cudaFree on all cached but unused blocks, retries. If it still fails, raises torch.cuda.OutOfMemoryError. Unlike CPU OOM, there's no kernel-level killer — your Python exception handler runs. Best practice: wrap the forward pass in try/except, log the OOM, and reduce batch size dynamically.

The CPU's MMU translates virtual addresses to physical addresses using a page table. For standard 4KB pages, a 10GB working set needs 2.5M page table entries. Accessing each unique entry requires a TLB lookup; with 64 TLB entries total, the miss rate is astronomical.

Huge pages (2MB or 1GB) reduce the number of page table entries by 512-262,144×, dramatically improving TLB hit rate for large memory workloads.

Enable transparent huge pages: echo always > /sys/kernel/mm/transparent_hugepage/enabled Allocate explicit 1GB huge pages: echo 16 > /sys/kernel/hugepages/hugepages-1048576kB/nr_hugepages # 16 × 1GB pages Pin with: numactl --membind=0 --hugetlbfs-shm ... Verify: cat /proc/meminfo | grep Huge HugePages_Total: 16 HugePages_Free: 12 ← 4 pages in use

When it helps AI workloads: DataLoader workers with large dataset pre-loading, where millions of 4KB page table entries cause TLB thrashing. In benchmarks I've run, enabling 2MB transparent huge pages for a ResNet ImageNet training run reduced DataLoader CPU overhead by ~8-12% — not huge, but free.

When it doesn't help: The model's CUDA memory is managed by the GPU's MMU, not the CPU's TLB — huge pages have zero effect on GPU memory access. And if your working set fits in L3 cache, TLB misses never happen anyway.

Follow-up: "What's the downside of always-on transparent huge pages?" → Khugepaged (the kernel daemon that collapses 4KB pages into 2MB pages) can cause occasional latency spikes as it scans memory. For latency-sensitive real-time serving, transparent huge pages can add P99 latency outliers. The fix is transparent_hugepage/defrag = madvise — only collapse pages for memory regions explicitly annotated with madvise(MADV_HUGEPAGE).
Real-World Scenarios — Open-ended debugging and design questions based on situations you encounter in production AI infrastructure. A principal engineer should be able to work through these end-to-end, not just name tools but actually diagnose.

The testing vs production gap is almost always explained by one of four factors: load pattern differences, infrastructure differences, software version differences, or measurement methodology errors.

  • 1. Replicate the discrepancy. Run the testing benchmark script in production. If it shows 150 tok/s, the issue is production traffic characteristics. If it shows 60 tok/s, it's infrastructure or software.
  • 2. Load pattern differences. Testing: batch=1, fixed 100-token outputs. Production: variable-length outputs, concurrent requests. At batch=1, decode throughput reflects burst performance. Under load with 20 concurrent users, the KV cache may fill, causing eviction and recomputation — check vllm.num_preemptions metric.
  • 3. Thermal throttling. Tests run for minutes; production runs continuously for hours. Check: nvidia-smi --query-gpu=clocks.sm --format=csv -l 1. If GPU base clock is 2505MHz but production shows 1800MHz, thermal throttling is dropping throughput ~30%.
  • 4. GPU memory fragmentation under sustained load. After hours of serving, the CUDA allocator may have fragmented memory, forcing fallback to smaller allocations or OOM retries. Periodically restart the serving process to reset allocator state, or use PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True.
  • 5. P2P transfer overhead from wrong NUMA binding. Testing ran on the same GPU; production load balancer might route to a GPU whose PCIe root is on a different NUMA socket from where the OS scheduled the serving workers.
Production monitoring setup I'd add immediately: nvidia-smi --query-gpu=utilization.gpu,memory.used,clocks.sm --format=csv -l 10 + vLLM metrics endpoint: /metrics (Prometheus-compatible) Key vLLM metrics: vllm:gpu_cache_usage_perc ← KV cache fill rate vllm:num_preemptions ← KV evictions → recompute overhead vllm:e2e_request_latency ← P50/P95/P99 latency vllm:time_to_first_token ← TTFT distribution

NaN loss that appeared after many steps but not at step 0 is typically a numerical stability issue triggered by a specific data batch or a parameter drift. Not a code bug per se — a numerical edge case.

  • 1. Find the exact step. Add torch.autograd.set_detect_anomaly(True) — it adds overhead but pinpoints the exact operation that produced NaN. In the traceback, it shows "Function X returned NaN at position Y."
  • 2. Was it a bad batch? Log the random seed and batch index when NaN occurs. Rerun with the same seed to reproduce. If a specific image has extreme pixel values (all-black, corrupted) it can cause log(0) = -inf in certain loss functions.
  • 3. Check the GradScaler if using AMP. scaler.get_scale() should be > 1. If scale has been reduced to very small values (below 1e-4), the loss is underflowing even before backward. This happens when gradients are consistently inf/nan — the scaler keeps halving.
  • 4. Check for exploding gradients. Log torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1e10) (huge clip) and print the norm each step. If you see a sudden spike from ~1.0 to 1e6 on step 999, an attention head's weights have diverged. Fix: reduce learning rate, add gradient clipping at max_norm=1.0.
  • 5. FP16 overflow. Activations in intermediate layers may overflow FP16 range (±65504). Common in deep networks during early training. Fix: use BF16 (same range as FP32), or add LayerNorm after every few layers to re-center activations.

The core challenge: Raw throughput numbers aren't comparable across hardware. You need to normalize to hardware-specific ceilings to compare efficiency, not just speed.

  • Roofline normalization: For each hardware configuration, first measure peak BW and peak FLOPs. Then express each workload's throughput as a percentage of the theoretical roofline.   • Fixed comparison points: Always compare at the same arithmetic intensity. LLM decode is always memory-bound; comparing its throughput on A100 vs H100 is straightforward. LLM prefill is compute-bound; the comparison should normalize by FLOP/s, not raw throughput.
  • Reproducibility requirements: Fix: CUDA driver version, PyTorch version, model checkpoint, tokenizer, random seeds, warmup count, measurement duration, GPU clock lock (sudo nvidia-smi --lock-gpu-clocks=base_clock to prevent boost variance).
  • Methodology for bottleneck shift analysis: The workload_port.py script pattern — run the same model (same weights, same inputs) in each configuration, report the efficiency and the bottleneck signal (ncu SM vs DRAM throughput). The bottleneck label should be part of the benchmark output, not left to interpretation.
